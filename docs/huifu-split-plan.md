# 分账实现总结与执行计划

更新时间：2026-02-26

## 当前状态总结（基于项目代码）
- 已有实时分账：`jspay_goods` 会在下单时构造 `acct_split_bunch`，按平台费率分给平台与卖家（实时分账）。
- 延时分账未接入购买流程：已有 `delay_confirm` 动作与测试入口，但尚未接到任务完成逻辑。
- 注册仅做实名核验：注册只上传身份证正面并通过腾讯 OCR 校验；未采集银行卡/开户地址/证件有效期等信息。
- 用户汇付开户未自动化：未在注册流程中自动调用 `user_indv_open`；`user_busi_open` 也未接入。
- 资金沉淀/提现逻辑未实现：没有“金额阈值 + 提现”闭环，未记录钱包余额与提现状态。

## 已确认的业务决策
1. 分账模式：实时分账 + 延时分账都需要。
2. 分账比例：用户 96%，平台 4%（3% 佣金 + 1% 平台扣费）。
3. 提现门槛：50 元。
4. 注册即开户：注册完成自动创建汇付用户。
5. 绑卡时机：提现时再绑定银行卡。

## 仍需确认的业务决策
1. 提现规则：到账周期、是否允许拆分确认。

## 关键业务说明（先对齐认知）
- `huifu_id`：用户在汇付体系里的“账户编号”。有了它，才能把分账金额打到这个用户的汇付账户里。
- 绑卡/入驻（`user_busi_open`）：用于配置结算卡/提现规则。没有绑卡时，钱仍在汇付体系内，不会直接到用户银行卡。
- 延时分账：如果下单时 `delay_acct_flag=Y`，钱会先在延迟户里；需要任务完成后 `delay_confirm` 才会真正分给平台/用户。

## 范围与目标
- 目标：实现“任务支付 -> 分账 -> 钱包沉淀 -> 满 50 元提现”的闭环；支持实时分账与延时分账两种模式。
- 约束：注册阶段不采集银行卡信息；提现时补绑卡。

## 数据模型草案（用于任务拆分与接口落地）
- `userInfo` 新增字段（建议）：`huifu_id`、`huifu_open_status`、`huifu_opened_at`、`huifu_open_fail_reason`。
- `wallet_ledger`（建议新集合）：记录余额流水与状态（`pending` / `available` / `withdrawn` / `failed`）、订单号、用户ID、金额、关联任务ID、时间戳。
- `withdraw_request`（建议新集合）：提现申请记录（金额、状态、银行卡摘要、申请时间、处理结果）。
- 任务/订单状态：`paid` -> `completed` -> `split_confirmed` -> `available`（可提现）。

## 关键流程定义
1. 注册 -> 自动开户（`user_indv_open`）-> 保存 `huifu_id`。
2. 任务支付：
   - 实时分账：下单时带 `acct_split_bunch`。
   - 延时分账：下单时 `delay_acct_flag=Y`，资金进入延迟户。
3. 任务完成：
   - 实时分账：仅做钱包入账（`available`）。
   - 延时分账：调用 `delay_confirm` 后再入钱包（`available`）。
4. 提现：
   - 余额 >= 50 且已绑卡 -> 发起提现 -> 成功后更新 `withdrawn`。
   - 未绑卡 -> 引导补银行卡信息并调用 `user_busi_open`。

## 执行计划（按顺序）

### 1) 汇付配置与权限确认
- 确认已开通：分账权限、延时分账权限（如选延时）、用户开户/入驻接口权限。
- 配置云函数环境变量：`HUIFU_SYS_ID` / `HUIFU_PRODUCT_ID` / `HUIFU_HUIFU_ID` / 私钥等。
- 明确测试环境与生产环境的 API Host。
 - 明确是否需要 webhook/notify（交易回调、分账回调）。

### 2) 用户开户（注册完成自动开户）
- 注册成功后调用 `user_indv_open` 创建汇付用户，拿到 `huifu_id`。
- `userInfo` 中保存：`huifu_id`、开户状态、开户时间、失败原因（便于批量补偿）。
- 如果开户失败，不影响注册，但标记“需补开户”。
 - 补偿机制：定时任务扫描 `huifu_open_status!=success` 进行重试。
 - 管理员补偿：提供一个“管理员重试开户”的入口（用于人工兜底；后续做管理后台时接入）。
 - 按汇付文档（个人用户基本信息开户 `/v2/user/basicdata/indv`）的“最少必填信息”补齐采集：
  - 用户侧最少需要提供：姓名、身份证号、身份证有效期（是否长期 + 起始日期；非长期还要截止日期）、手机号。
  - 系统侧生成/维护：`req_seq_id`（每次请求的唯一编号，像“请求单号”）、`req_date`（yyyyMMdd）。
  - `cert_type` 固定用身份证（一般是 `00`），并保持和你们现有的身份证 OCR/校验逻辑一致。
 - 证件有效期的采集策略（避免增加用户负担）：
  - 优先做“手填 + 长期有效开关”；后续如体验需要，再考虑加“身份证反面 OCR”（能自动读到有效期）。
 - 预留扩展位：汇付接口支持 `file_list`（证件照等），先按“只传文字信息”的最少方案对接；如果后续汇付侧要求更严格再补。

### 3) 绑卡/结算配置（提现前补齐）
- 新增“银行卡信息”采集页（持卡人、卡号、开户行省市、证件有效期等）。
- 调用 `user_busi_open` 配置结算卡/结算规则。
- 仅在用户达到提现门槛时引导补卡。
 - 绑卡成功后，将银行卡摘要（卡号后四位/银行名称）保存到用户资料。
 - 按汇付文档（用户业务入驻 `/v2/user/busi/open`）的“个人对私卡”最少必填信息落地：
  - 只允许个人对私同名卡：`card_type=1`（避免对公/非同名导致需要上传营业执照等材料）。
  - 用户侧最少需要提供：银行卡号、开户行省/市（`prov_id`/`area_id`，就是省市对应的数字编码）、银行卡预留手机号（`mp`，你在银行留的那个手机号）。
  - 证件信息复用开户信息：`cert_type/cert_no/cert_validity_type/cert_begin_date/cert_end_date`（对私必填）。
  - `card_name` 建议直接用开户的“姓名”，避免用户重复填写。
 - 省市编码（`prov_id`/`area_id`）任务：
  - 前端做省/市选择器；后端或前端把选择结果映射成编码（可以放一份编码表 JSON 做本地映射，避免每次网络查询）。
 - 绑卡信息存储任务（减少风险）：
  - 数据库只保存卡号后四位 + 银行名称/简称；完整卡号只在提交汇付时短暂使用（尽量不落库）。

### 4) 钱包与提现门槛
- 新增钱包流水：`pending` / `available` / `withdrawn` / `failed`。
- 配置提现门槛（比如 50 元），达到后允许提现操作。
- 若未绑卡，提示“先补银行卡”。
 - 钱包余额以“可提现余额 available”为准；任务完成前仅记录 `pending`。

### 5) 任务支付与分账落地
- 前置检查（强制）：分账接收方必须已开户（有 `huifu_id` 且 `huifu_open_status=success`）。
 - 若未开户：直接提示“对方暂未开通收款，无法分账/支付”，并引导对方先完成注册或管理员协助重试开户。
- 任务发布者 A 支付时：
  - 实时分账：下单时直接带 `acct_split_bunch`。
  - 延时分账：下单时 `delay_acct_flag=Y`，任务完成后再 `delay_confirm`。
- 任务完成后：
  - 实时分账：只更新钱包状态与流水。
  - 延时分账：调用 `delay_confirm` 分配给平台与用户 B。
- 分账比例统一为：用户 96%，平台 4%（3% 佣金 + 1% 平台扣费）。
- 说明：延时分账是“资金确认时机”，提现门槛是“钱包规则”，两者可同时存在。

### 6) 提现与结算
- 用户触发提现时：检查余额>=门槛 && 已绑卡。
- 调用对应的汇付提现/结算流程（待确定具体 API）。
- 回写提现状态与结果（成功/失败/处理中）。
 - 如果提现失败：回滚钱包状态或进入“可再次提现”状态。

### 7) 测试用例
- 单笔 3 元：
  - 平台 4% = 0.12 元，用户 2.88 元。
- 延时分账测试：
  1) 下单 `delay_acct_flag=Y`
  2) 任务完成后 `delay_confirm`
- 钱包累计测试：累计多笔任务，达到门槛后触发绑卡+提现。
 - 幂等测试：重复请求同一 `req_seq_id` 不应产生重复入账。
