# 来源头像资料延迟回填修复

## 现象与根因

- 个别新资讯已经有正文和原文截图，但卡片与详情仍显示首字母头像。
- 生产数据库中的作者档案和云头像对象都已存在，头像对象重新换签后可正常读取；因此问题不在当前公网中继，也不是头像下载或 Cloud Storage 读取失败。
- AIHOT 正文流有时先于可选作者资料流出现新条目。旧逻辑只有在作者资料流已经包含该条目时才读取作者档案缓存；若两者短暂错开，正文条目会先以无头像状态入库，后续相同内容指纹又可能跳过完整回填。

## 修复

- 把 X 原帖地址中的账号提取收敛到共享来源资料模块，并只接受精确的 `https://x.com/` 或 `https://www.x.com/` 地址与合法账号格式。
- 作者资料增强服务现在会为本批全部 X 原帖读取已有作者档案；即使上游作者资料尚未传播到该条目，也能按原帖账号补回已缓存的昵称、账号与头像 File ID。
- 上游作者资料接口临时失败时继续使用现有档案回填，不阻断正文同步，也不清空已有标签和来源资料。

## 生产验证

- `knowledgeFeed` 已部署新逻辑并执行一次强制全量刷新；本轮检查 2,110 条当前资讯，只更新 1 条资料缺口，没有新增视觉或分析任务。
- 用户指出的目标资讯刷新后同时具备作者身份和头像 File ID；对应头像临时地址返回 HTTP 200、`image/webp`，正文截图保持不变。
- 生产截图函数仍只配置当前公网中继；旧公网节点不在生产路径。本次头像事件不经过截图中继，不能用代理稳定性解释。

## 验证

- 来源资料专项测试 9/9 通过，包含“正文先到、作者资料晚到、已有作者档案可回填”的回归场景。
- 全量 Node 测试 437/437 通过；项目检查覆盖 35 个 JSON、267 个 JavaScript 和 11 个页面；`git diff --check` 通过。
