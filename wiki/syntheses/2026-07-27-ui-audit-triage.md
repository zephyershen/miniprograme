# 小程序 UI 与功能审计分流及首批加固

## 结论

2026-07-27 收到的外部审计总体有价值，但混合了三种不同性质的事项：

1. 已有兼容性缺陷和低风险维护项；
2. 需要分页面验证的视觉系统改造；
3. 需要新数据合同、平台配置和产品验收的新功能。

不应按原清单逐条连续改完。当前仍应先完成会员专栏管理端的小程序审核和真实管理员
canary；不影响该发布链路的低风险修复可以合并，其余内容另行分批。

## 已确认并落地

- 微信 `style: "v2"` 的按钮可能保留原生最小宽度，固定宽按钮与 `flex: 1`
  按钮并排时会挤压或溢出。`app.wxss` 的全局 `button` 基线已加入
  `min-width: 0`，同时保护资讯页和精选页的筛选操作行。
- 资讯首页的 timeline、lead、remaining 三种容器原先复制了同一套卡片正文。
  现已改为同页 `feed-post-card` WXML 模板，三个容器只负责传入内容和媒体状态路径。
  头像、图片恢复、来源标签、评论、喜欢、收藏和分享绑定保持不变。
- 对应合同测试改为验证“单一卡片模板 + 三个调用点”，不再把三份复制代码误当成
  正确行为。

## 审计中需要修正的判断

- 硬编码色值数量能说明需要盘点，不能直接证明每个色值都是设计漂移。状态色、媒体
  占位色和语义色不能做全局搜索替换；后续应按核心灰阶、品牌色、状态色分层迁移。
- `column-reader` 的图片错误目前确实只有提示，没有自动重新签发和重试；但阅读器
  已挂载当前及相邻图片窗口，所以“完全没有预取下一页”并不准确。
- `trend-detail` 虽然没有主导航入口，仍承担旧深链和关联趋势的兼容路由，并有回归
  合同保护。不能按“死路由”直接删除，除非产品明确结束兼容期。
- 深色模式不是简单补 `darkmode` 与 `theme.json`。当前页面存在大量显式颜色、图片
  和长文状态，必须先完成 token 收敛和全页真机验收。
- Tab 图标、统一下拉刷新和 44px 点按热区都值得评估，但会改变可见界面或交互，
  应独立验收，不属于零风险资源修改。

## 建议顺序

1. 先完成当前专栏管理端审核与真实管理员 canary，并保留本次按钮基线和卡片去重。
2. 第二批处理可访问性与一致性：关键点按热区、平台中立的数字字体、核心颜色
   token、确定无引用的死样式。
3. 第三批在重复合同明确后抽取空态和骨架组件，并逐页决定是否支持下拉刷新。
4. 阅读器可靠性优先补短期图片地址的单次重新签发和自动重试。
5. 新功能按“阅读进度 → 关键词搜索 → 订阅消息”排期；订阅消息必须先准备微信模板、
   用户授权、发送频率和失败处理，不作为纯前端功能推进。
6. 管理端条目增长后，再增加状态筛选、搜索和直接排序；在真实管理员 canary 前不
   扩大管理端交互面。
