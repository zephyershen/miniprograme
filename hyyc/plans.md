# HYYC 商品系统（类咸鱼）完整计划清单（按开发顺序）

目标：把「商品」这条线做成“像咸鱼那样好用”的二手交易：列表顺滑、详情清楚、能聊、能拍下、能付款、平台先收钱，确认收货后再给卖家（7 天自动给）。

说明：咸鱼的功能非常多，我们这里按“二手交易核心体验”去做到 99%+。有些事情不只是写代码，还涉及微信支付/合规/风控（防骗防刷），需要先确认条件。

补充：你现在是开发阶段，旧数据不考虑，已有集合字段都可以按本计划调整。

## 1. 数据（云数据库集合）规划（先把地基打好）

### 1.1 现有集合（已在用）

- `goods`：商品（已实现发布 + 列表）
- `userInfo`：实名用户信息（含手机号、门牌等敏感信息）
- `messages`：任务聊天消息（已实现）
- `tasks`：任务（已实现）

### 1.2 建议新增集合（类咸鱼交易必备）

为了“性能像咸鱼”（不卡、查得快），建议把数据拆清楚：

1) `goods_orders`（订单）
- 一条订单对应“一个商品的一次拍下”
- 关键字段建议：
  - `goodsId`
  - `sellerId` / `buyerId`
  - `status`（状态建议：待付款/已付款待交付/争议中/退款中/已完成/已关闭…）
  - `goodsSnapshot`（下单时把标题、图片、价格等复制一份，避免卖家改了导致对不上）
  - `payAmount`（最终要付多少钱，支持卖家改价）
  - `tradeType`（当面/邮寄；你当前以当面为主）
  - `createdAt` / `paidAt` / `receivedAt` / `closedAt`
  - `payExpireAt`（例如创建订单后 +5 分钟，超时自动关单）
  - `autoConfirmAt`（例如付款后 +7 天，自动确认收货并放款）
  - `platformFeeRate` / `platformFeeAmount`（平台服务费：费率后定，但建议在放款时扣）

2) `goods_order_events`（订单事件流水，可选但强烈建议）
- 用来记录“谁在什么时候做了什么”，以后查纠纷很有用
- 例子：买家拍下/卖家改价/买家付款/卖家标记已交付/买家确认收货/系统 7 天自动确认等（邮寄以后再加发货/物流）

3) `chat_conversations`（会话表，建议做）
- 目的：像微信那样的“聊天列表”能秒开，不用扫全量消息
- 字段例子：
  - `convId`（会话编号：像“文件夹编号”，确保不会串聊天）
  - `bizType`：`goods` / `task`
  - `bizId`：商品 id 或任务 id
  - `ownerId`（卖家/任务发布者）
  - `peerUserId`（另一方）
  - `ownerOpenid` / `peerOpenid`（用来做权限：只让会话双方看见）
  - `lastMsgText` / `lastMsgType` / `lastMsgAt`
  - `unreadByOwner` / `unreadByPeer`

4) `chat_messages`（聊天消息）
- 你现在开发阶段“不考虑旧数据”，建议直接做成“通用聊天”：
  - `convId`（会话编号：进入聊天框时只查这个 `convId`，就不会加载到别人的消息）
  - `bizType`：`goods` / `task`
  - `bizId`：商品 id / 任务 id
  - `fromUserId`
  - `ownerOpenid` / `peerOpenid`（用来做权限：只让会话双方读写）
  - `msgType`：`text` / `image` / `system`（system=系统提示，比如“已拍下/已付款/申请查看手机号”等）
  - `text` / `imageUrl` / `payload`（payload=额外信息，比如订单号、要展示的按钮等）
  - `createdAt`（用服务器时间，保证排序稳定）
  - `readByOwner` / `readByPeer`
  - （可选）`clientMsgId`（客户端生成的随机号，防止网络抖动导致“重复发一条”）

5) `goods_favorites`（收藏）
- 字段：`goodsId`、`userId`、`createdAt`
- 可再加：`favoriteCount` 回写到 `goods`（列表上显示“多少人想要”，也更像咸鱼）

6) `goods_reports`（举报）
- 字段：`goodsId`、`reporterId`、`reason`、`createdAt`、`status`

7) `user_blocks`（拉黑/屏蔽）
- 字段：`userId`、`blockedUserId`、`createdAt`

8) `wallet_accounts` / `wallet_flows`（平台托管钱的“钱包”）
- `wallet_accounts`：每个人一个账户（余额/冻结中金额）
- `wallet_flows`：每一笔钱的流水（像银行流水）
- 备注：这部分是否“真自动打款”，取决于第 0 节第 2 条能不能做。

9) `user_contact_requests`（申请查看完整信息）
- 用在聊天里：买家点“申请查看”，卖家选择同意并勾选要开放的字段
- 字段例子：
  - `fromUserId`（申请人）
  - `toUserId`（被申请人，比如卖家）
  - `bizType` / `bizId`（来自哪个商品/订单）
  - `fields`（允许看的字段：phone/name/door 等，按你想开放的范围定义）
  - `status`（pending/approved/rejected）
  - `createdAt` / `handledAt`

10) `user_ratings`（交易后互评/点赞）
- 字段例子：
  - `orderId`
  - `fromUserId` / `toUserId`
  - `level`（四档：非常好/很好/一般/差）
  - `createdAt`
- 规则建议：同一笔订单里，同一方只能评一次（防止刷评价）

### 1.3 数据库权限规则（很重要）

- `userInfo` 绝对不建议让所有人可读（否则手机号/门牌会泄露）
- “别人能看到的卖家信息”建议由云函数返回，并且只返回“打码后的信息”
  - 打码例子：手机号 `138****8000`；姓名 `张*`；门牌 `11栋 7**`（具体怎么打码按你定）

### 1.3.1 每个集合建议权限（按云开发控制台能选的那几项来）

你在控制台能选的就是这几类（和你截图一样）：
- `所有用户可读，仅创建者可读写`
- `仅创建者可读写`
- `所有用户可读`
- `所有用户不可读写`
- `自定义安全规则`

注意两句（很重要）：
1) 如果你选了 `仅创建者可读写`，那“另一方”就读不到（比如聊天就会失败）。
2) 如果你选了 `所有用户不可读写`，小程序端就完全不能直接查/写；只能走云函数（云函数=你的小程序后台小帮手）。

按我们“商品交易优先，任务先不管”的节奏，建议这样选：

- `userInfo`：选 `仅创建者可读写`
  - 目的：保护手机号/门牌等敏感信息
  - 别人要看的信息（打码/授权后的完整信息）统一走云函数返回

- `goods`：
  - 开发自测阶段：可以先选 `所有用户可读，仅创建者可读写`（方便你自己调试列表/详情）
  - 上线前（需要审核不泄露）：建议改成 `自定义安全规则`，只让“审核通过+上架”的商品能被别人读到

- `chat_conversations` / `chat_messages`（聊天两张表）：
  - 建议直接选 `自定义安全规则`（只允许“会话双方”读写）
  - 因为用前面那 4 个固定选项，要么会泄露（所有人可读），要么会导致另一方看不到（仅创建者可读写）

- `goods_orders` / `goods_order_events`（订单相关）：
  - 建议选 `所有用户不可读写`
  - 原因：订单状态/金额很敏感，最好都由云函数来创建、改价、确认收货、退款（小程序端只“调用云函数拿结果”）

- `wallet_accounts` / `wallet_flows`（钱包/流水）：
  - 建议选 `所有用户不可读写`（金额相关一律走云函数）

- `goods_favorites`（收藏）：
  - 选 `仅创建者可读写`（别人不应该知道你收藏了什么）

- `user_blocks`（拉黑）：
  - 选 `仅创建者可读写`

- `user_contact_requests`（申请查看完整信息）：
  - 推荐做法：选 `所有用户不可读写`，由云函数创建/同意/拒绝并返回结果（最安全、逻辑也最清晰）
  - 如果你想先简单一点：也可以先选 `所有用户可读，仅创建者可读写` 做调试，但上线前一定要收紧

- `user_ratings`（互评）：
  - 推荐：选 `所有用户不可读写`，由云函数写入；前端只拿统计

- `goods_reports`（举报）：
  - 推荐：选 `仅创建者可读写`（举报人只能看自己的举报；管理员通过云函数后台查询全部）

### 1.4 必要索引（先记清单，等代码稳定+有数据后再建）

你说的对：现在先不建也可以。等“功能跑通 + 数据长起来”后再建索引，效果更明显，也更不容易返工。

提醒一句：唯一索引一旦建了，只要出现重复数据，那条写入会直接失败（所以唯一索引要按下面的规则来建）。

- 说明：索引有两种：
  - 非唯一：只是“查得快”，允许重复
  - 唯一：像“每张身份证号只能有一个人”那样，不能重复（用来防止重复收藏/重复互评等）

- `goods`
  - 非唯一：`community + reviewStatus + createdAt`（列表页）
  - 非唯一：`community + category + createdAt`（分类筛选）
  - 非唯一：`ownerId + createdAt`（我的发布）
- `chat_conversations`
  - 唯一：`convId`（一对人+一个商品/任务=一个会话，防止重复建会话）
  - 非唯一：`ownerId + lastMsgAt`（会话列表）
  - 非唯一：`peerUserId + lastMsgAt`（会话列表）
- `chat_messages`
  - 非唯一：`convId + createdAt`（进聊天框按时间分页加载）
  - （可选）唯一：`clientMsgId`（如果你做了“防重复发消息”，可以加这个）
- `goods_orders`
  - 唯一：`orderNo`（你自己生成的订单号，用来防重复下单/防重复回调）
  - 非唯一：`buyerId + createdAt`（买家订单列表）
  - 非唯一：`sellerId + createdAt`（卖家订单列表）
  - 非唯一：`goodsId`（从商品找订单）
  - 非唯一：`status + createdAt`（管理员审核/处理列表）
- `goods_order_events`
  - 非唯一：`orderId + createdAt`（订单事件按时间展示）
- `goods_favorites`
  - 唯一：`userId + goodsId`（防止一个人重复收藏同一件）
  - 非唯一：`userId + createdAt`（我的收藏）
  - 非唯一：`goodsId + createdAt`（统计收藏趋势/后台用）
- `user_contact_requests`
  - 唯一：`bizType + bizId + fromUserId + toUserId`（同一商品同一对人只保留一条申请记录）
  - 非唯一：`toUserId + createdAt`（卖家处理申请列表）
  - 非唯一：`fromUserId + createdAt`（买家查看申请进度）
- `user_ratings`
  - 唯一：`orderId + fromUserId`（同一订单同一方只能评一次）
  - 非唯一：`toUserId + createdAt`（个人页统计/后台用）

## 3. 核心流程（按咸鱼体验拆）

### 3.1 浏览 -> 详情

- 列表点卡片进入详情
- 详情展示：所有图片、价格、原价、标题、描述、分类、成色、交易方式、发布时间、同小区/楼栋信息

### 3.2 详情 -> 聊一聊

- 点“聊一聊”进入与卖家的单聊
- 聊天里能发文字/图片
- 聊天列表能看到未读数和最新一条消息

### 3.3 详情 -> 拍下 -> 付款 -> 托管

- 点“购买/拍下”：
  - 生成订单（待付款）
  - 商品被暂时锁定（别人暂时买不了）
- 付款成功：
  - 订单变“已付款”
  - 资金进入“平台托管”

### 3.4 当面交付 -> 确认收货 -> 放款给卖家

- 你当前以“线下当面交易”为主：
  - 买家付款后，线下见面拿到商品
  - 买家点“确认收货”后，平台放款给卖家（并扣平台服务费）
- 如果买家一直不点确认：付款后 7 天自动确认收货并放款
- 如果有退款/争议：进入“争议中”，暂停自动放款，等客服处理完再决定退/放款

### 3.5 改价（拍下未付款场景）

- 买家拍下未付款 -> 在订单里/聊天里发起“请求改价”
- 卖家可改订单金额
- 买家按新金额继续付款

### 3.6 超时自动处理（系统像闹钟一样自动做事）

- 订单待付款超过 5 分钟：自动关闭，商品恢复可买
- 订单已付款超过 7 天未确认：自动确认收货并放款（但如果在退款/争议中，就不自动放款）

### Phase E：聊天（商品维度的“我和卖家的对话”）

- [ ] 聊天数据升级为“通用会话”（先做 goods；task 后面复用同一套）
- [ ] 定义 `convId` 规则（会话编号）：`bizType + bizId + ownerId + peerUserId`
  - 原则：同一个商品同一对人，永远算出同一个 `convId`，这样消息不会串
- [ ] 会话列表页：只查 `chat_conversations`（快），不扫 `chat_messages`（数据多了会慢）
- [ ] 商品详情点“聊一聊” -> 自动创建/进入该商品会话（带 `convId`）
- [ ] 聊天框加载：
  - 只查 `chat_messages where convId`（只会拿到这一个会话的消息，不会错乱）
  - 按 `createdAt` 排序；同一时间点再按 `_id` 兜底（保证顺序稳定）
- [ ] 发消息时同步更新 `chat_conversations`：
  - 更新 lastMsg、lastMsgAt
  - 给对方未读数 +1，自己未读不加
- [ ] 聊天里显示商品卡片（可选：顶部展示该商品摘要，像咸鱼）
- [ ] 聊天页隐私：买家可“申请查看完整信息”，卖家可同意/拒绝，并勾选开放哪些信息（手机号/姓名/门牌等）
- [ ] 授权通过后：仅在该会话里展示卖家被授权的完整信息（建议可设置有效期，比如 24 小时）
- [ ] 未读数：进房间自动置已读（复用/改造现有云函数）
- [ ] 聊天分页：只加载最近 N 条，往上滑再加载更早的（避免消息多了卡）

### Phase F：拍下（订单创建 + 商品锁定）

- [ ] 新建订单集合 `goods_orders`
- [ ] “拍下”按钮 -> 调云函数创建订单（服务端做校验更安全）
  - 校验：商品是否还在上架、是否属于本小区、是否已被别人拍下
  - 原子操作（事务=要么都成功要么都失败）：创建订单 + 锁定商品
- [ ] 订单确认页：显示商品信息、支付金额、交易方式（你当前默认当面交易）
- [ ] 当面交易提示：付款前提示“请当面验货后再付款”（可加勾选确认，减少纠纷）
- [ ] 订单超时未付款自动关闭：5 分钟到点自动关单并解锁商品（页面可显示倒计时）

### Phase G：微信支付接入（平台收钱）

- [ ] 支付前置条件（你已绑商户号/已企业认证）：补齐证书、回调地址、退款权限、回调验签等
- [ ] 云函数：创建预支付单（prepay）并返回给小程序调起支付
- [ ] 支付结果回调：更新订单为已付款（要能防止重复回调）
- [ ] 支付失败/取消：订单保持待付款，可再次支付
- [ ] 对账与兜底：支付成功但订单没更新时能补偿修复

### Phase H：平台托管资金（先收钱，后给卖家）

- [ ] 设计钱包：`wallet_accounts` / `wallet_flows`
- [ ] 付款成功：钱记到“平台托管-冻结中”
- [ ] 买家确认收货：触发“解冻 -> 记到卖家可用余额”（放款时扣平台服务费）
- [ ] 7 天自动确认：到期自动确认并解冻给卖家（但退款/争议中不自动放款）
- [ ] 平台服务费：先做“可配置费率/固定金额”，等你核算成本后再改具体数
- [ ] 卖家提现：
  - 方案 A：自动转账到卖家微信零钱（看微信是否允许）
  - 方案 B：先做“提现申请”，后台人工打款（先跑起来）

### Phase I：线下交付/确认收货（本期以当面为主）

- [ ] 订单详情页：买家按钮“确认收货”（提示：确认后平台会把钱放给卖家）
- [ ] （可选）卖家按钮“已交付”（双确认更安全：双方都点了才算完成）
- [ ] 自动确认：付款后 7 天未确认 -> 系统自动确认并放款（但退款/争议中不自动）
- [ ] 订单状态文案：让用户一眼看懂自己该干什么（待付款/待交付/待确认/已完成/已关闭/退款中/争议中）
- [ ] （后续可选）邮寄交易：地址管理/快递单号/物流查询

### Phase I2：互评/点赞（简版）

- [ ] 订单完成后：聊天页/订单页出现“互评小气泡”（非常好/很好/一般/差）
- [ ] 双方各评一次：同一订单同一方只能评一次（防刷）
- [ ] 卖家/买家信息页展示互评统计（只显示数量，不展示评价人）

### Phase J：改价（拍下未付款才允许）

- [ ] 卖家在订单里“改价”
- [ ] 改价记录写入 `goods_order_events`
- [ ] 买家看到新价格并可继续付款
- [ ] 风控：改价需要限制次数/幅度（避免乱改）

### Phase K：售后/退款/争议（咸鱼体验里很关键）

- [ ] 退款申请：仅限“已付款但未确认收货”的订单，买家可发起（选原因 + 文字/图片举证）
- [ ] 卖家处理：同意 -> 原路退款；拒绝 -> 买家可点“申请平台介入”
- [ ] 超时处理（建议初版）：买家发起退款后，卖家 24 小时内不处理 -> 自动进入“争议中”，由客服跟进（不直接自动退款）
- [ ] 争议中：资金继续托管，不走 7 天自动放款，等客服处理完再决定退/放款
- [ ] 客服入口：订单详情/争议页放“联系客服”（按钮可用 `open-type="contact"`，或用 `wx.openCustomerServiceChat` 接企业微信客服）
- [ ] 售后时限（建议初版）：付款后 7 天内可发起；确认收货后默认不支持退款（特殊情况走客服）

### Phase L：卖家管理（编辑/下架/已售）

- [ ] 我的发布商品列表
- [ ] 编辑商品（标题/描述/价格/图等）
- [ ] 下架/上架

### Phase M：安全与合规（防骗、防刷、防违规）

- [ ] 商品审核（上线前必须有）：新商品默认 `pending_review`，审核通过才出现在列表/搜索

- [ ] 拉黑：拉黑后双方不能再聊天/看对方商品（至少不推荐/不进入）
- [ ] 频控：同一用户短时间发太多商品/消息要限制（防刷屏）

### Phase N：性能与体验（对标咸鱼“顺滑”）

## 5. 你刚才没提但很容易踩坑的点（建议提前做）

1) “谁能看见谁的信息”要定死（尤其手机号/门牌）
2) 订单和商品状态必须锁住（避免两个人同时拍下同一件）
3) 支付/退款要做“重复回调不出错”（幂等=多来一次也不会多扣一次钱）
4) 聊天不要用“扫全库聚合”做列表（量大就会慢），最好有会话表
5) 需要最简的“平台介入/举报”入口，不然出纠纷没法处理
6) 聊天防错乱：一定要用 `convId`（会话编号）做隔离，所有查询都带 `convId`，不要只用“对方 id”去查
